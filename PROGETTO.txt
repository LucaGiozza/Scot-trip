1. COS'È L'APP
================================================================================
App web personale (NON commerciale) per documentare un viaggio in Scozia di
coppia, dal 4 al 13 settembre 2026. Itinerario: Edimburgo, Stirling, Inverness,
costa del Moray, Isola di Skye, Glencoe, Glasgow.

Funzionalità principali:
- Itinerario giorno per giorno (10 giorni, 45 tappe).
- Per ogni tappa: descrizione, info pratiche (orari/costi/prenotazioni),
  2-3 "curiosità" vere (categorie: Assurdo ma vero / Storia / Leggenda),
  link a Google Maps, badge "Da vedere" → "✓ Visto".
- Foto ricordo per ogni tappa, pasto e alloggio (scatto/caricamento, compresse
  sul telefono, sincronizzate nel cloud).
- Voti di coppia (2 persone, 1-5 stelle):
    * Tappe: voto unico "Generale".
    * Pasti e Alloggi: 4 categorie → Location, Prezzo, Qualità, Personale.
- Pasti: nome locale, luogo, giorno, tipo pasto, "cosa abbiamo mangiato", costo,
  nota, foto, voti.
- Alloggi: nome, località, check-in/out, nota, foto, voti.
- Classifiche: podio generale + migliori per categoria, separate per Ristoranti
  e Alloggi.
- Pagina "Altro": accesso alle classifiche, "il viaggio in numeri" (tappe viste,
  foto, pasti, stelle), accesso alle impostazioni.
- Impostazioni: nomi dei viaggiatori, login account condiviso (Supabase), stato
  sincronizzazione.

Grafica: tema scozzese sobrio. Palette verde pino / blu notte / erica (viola) /
ginestra (oro), con nastri tartan SOTTILI come cornice. Gattino bianco con
sciarpa tartan come mascotte (schermata di caricamento, timbro sulle curiosità,
stati vuoti). Ogni tipo di tappa ha una "scenetta" illustrata dedicata e un
colore d'accento (castello, natura, spiaggia, distilleria, chiesa, panorama,
borgo, città).

IDEE ESPLICITAMENTE RIFIUTATE dall'utente (NON reintrodurre):
check-in GPS con animazione gatto, gatti collezionabili, passaporto timbri,
parola gaelica del giorno, contatore pecore, diario di coppia.

2. STACK TECNICO E ARCHITETTURA
================================================================================
- Frontend: Blazor WebAssembly standalone, .NET 8 (net8.0), come PWA.
  (MAUI è stato valutato e SCARTATO: complessità distribuzione iOS senza
   account sviluppatore. Non riproporlo.)
- Linguaggio: C# (l'utente programma in C# con Visual Studio).
- Hosting: GitHub Pages (gratuito), deploy automatico via GitHub Actions.
- Backend: Supabase (piano Free) = database Postgres + Storage foto + Auth.
- NIENTE SDK Supabase: si usano le REST API dirette (PostgREST / GoTrue /
  Storage) con HttpClient. Scelta deliberata per bundle più piccolo.
- Offline-first OBBLIGATORIO (Highlands e Skye senza rete):
    * Si scrive SEMPRE prima in locale (IndexedDB), poi si sincronizza.
    * Coda di operazioni in IndexedDB; push + delta-pull.
    * Conflitti: last-write-wins su updated_at (sia client sia trigger SQL).
    * Cancellazioni = "soft delete" (colonna deleted=true) così si propagano.
    * ID generati dal client (UUID). I voti usano un UUID DETERMINISTICO
      calcolato da (target, persona, categoria): così se entrambi votano la
      stessa cosa offline i due upsert convergono sulla stessa riga.
- iOS/Safari NON supporta la Background Sync API: la sync è guidata dall'app
  (all'avvio, quando torna online, al ritorno in primo piano, dopo ogni salvataggio).
- Foto: compressione client-side via canvas (lato max 1600px, JPEG qualità 0.8),
  blob salvato in IndexedDB, upload a Supabase Storage via fetch JS (il binario
  non passa mai per .NET). Foto dell'altro telefono viste con URL firmati
  (bucket privato).

NOTA IMPORTANTE per chi modifica il codice in futuro:
Il progetto Blazor WASM completo NON si compila in ambienti dove NuGet è
bloccato. Per verificare il codice offline si può usare un progetto "ombra"
con Sdk Microsoft.NET.Sdk.Razor + FrameworkReference Microsoft.AspNetCore.App
che compila .cs e .razor (escludendo Program.cs). Per i test visivi mobile si
usa Playwright/Chromium con un testbench HTML statico che carica il CSS reale a
viewport iPhone (390x844 e 320px), verificando assenza di overflow orizzontale.

5. FLUSSO DI LAVORO / DEPLOY
================================================================================
1. Modifica i file (in locale con Visual Studio, oppure direttamente su GitHub).
2. Carica su GitHub:
   - da riga di comando (consigliato):
       git add . && git commit -m "descrizione" && git push
   - oppure via web: "Add file" / matita, mantenendo le CARTELLE (non appiattire).
3. Il workflow deploy.yml parte da solo su push a main → tab "Actions" → verde ✅.
4. In ~2 minuti l'app è aggiornata su https://lucagiozza.github.io/Scot-trip/

CACHE (PWA) — importante durante lo sviluppo:
Dopo un deploy, gli iPhone possono mostrare la versione vecchia in cache.
Il CSS è versionato con ?v=NN in index.html: aumentare quel numero a ogni
modifica del CSS forza il refresh. Se l'app è installata sulla Home: chiuderla
del tutto e riaprirla DUE volte (il service worker aggiorna al primo avvio e
applica al secondo), o eliminare/riaggiungere l'icona.

ULTIMO INTERVENTO (v11) — bug tab bar inferiore:
Problema: passando da Itinerario (pagina lunga) a Pasti/Alloggi (pagina corta)
la tab bar in basso "si alzava" invece di restare ancorata.
Causa: la tabbar era position:fixed rispetto alla finestra; su iPhone la barra
indirizzi del browser appare/scompare cambiando l'altezza della finestra e
facendo saltare la tabbar.
Soluzione applicata: nuovo impianto layout. html/body/#app/.app-shell ad altezza
viewport fissa (100dvh, fallback 100vh); header e .tabbar sono blocchi fissi ai
bordi (flex 0 0 auto); SOLO <main class="app-main"> scorre (overflow-y:auto,
min-height:0). Così la tabbar non è più agganciata al fondo della finestra ma al
fondo dell'app e non può più saltare. Verificato con Playwright: tabbar nella
stessa posizione su pagina piena e vuota, ferma durante lo scroll, nessun
overflow a 390px e 320px.
→ DA CONFERMARE dall'utente sul telefono reale dopo il deploy v11.
